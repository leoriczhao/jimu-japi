# 引擎原生血条改造路线（ENGINE-HEALTHBAR）

> 状态：S0 侦察进行中（见 §4）。本文件记录方向、已确认的技术事实、阶段划分与验收口径。
> 前置文档：`docs/planning/HEALTHBAR-ROUTES.md`（5 条社区路线的对比矩阵）。
> 用户决策（2026-11-16）：「社区那种方案为主，以改造引擎的为主」→ 本文即该主线的执行方案。

## 1. 目标

把「头顶血条」从「我们的 D3D 自绘」切换为「引擎原生条 + 我们的策略」，消除 D3D 自绘的两个固有缺陷：

1. **采样滞后**：overlay 采样率（现 BAR_TICK=0.02，已顶到逻辑帧上限）永远 ≤ 逻辑帧，单位移动时条落后数帧。
2. **锚点靠估计**：1.27a 没有模型包围盒/附着点查询接口，头部高度只能用 `BAR_HEAD` 常量按单位类型实测拟合，地形高度变化时还会浮动。

引擎原生条锚在模型的 overhead 附着点上，天然跟手、天然遮挡排序正确、零采样延迟。

## 2. 为什么判定可行（证据）

| 证据 | 内容 |
|---|---|
| 引擎条确实存在且可整局常显 | 客户端偏好 `HKCU\Software\Blizzard Entertainment\Warcraft III\Gameplay\healthbars`（DWord，默认 0）置 1 后，引擎给**所有**单位画原生条；开机读一次，热改无效。 |
| 原生条几何已实测 | 9px 高；宽 85px（hfoo/hrif）、120px（hkni）、535px（基地）；**缩放 4 格后同一条仍 195→193px，即固定屏幕像素、不随镜头变**。行结构：黑框 1px / 高亮 (115,255,0) / 主体 (64,140,0) / 阴影 (41,91,0) / 黑框。 |
| 社区已证明引擎条可进程内改写 | 内存 hack 把引擎 HP/MP 条暴露为 JASS native：`SetHPCustomHPBarUnit(PlayerID, UnitID, Color, ScaleX, ScaleY)`、`SetHPBarColorForPlayer(PlayerID, HeroColor, UnitColor, TowerColor)`、`SetMPBarXScaleForPlayer`（xgm.guru / wc3edit / Hive）。 |
| 我们已在进程内，且有注入框架 | `src/src/yd_core/warcraft3/jass/inline_hook.cpp`（UnitId hook 在用）、`src/src/base/hook/`（iat/eat/dyn_iat）、`src/src/d3d9/CDirect3DDevice9.cpp`（完整 IDirect3DDevice9 代理，夹在引擎每次 draw 中间）。外部 `OpenProcess` 被拒（error 5），所以一切内存操作必须在进程内做。 |

## 3. 已确认的技术事实（本轮静态侦察）

- **偏好名不可静态追到读取点**：`healthbars` 字符串（静态镜像 VA `0x6F951530`，文件 off `0x950930`）在 Game.dll 里**只被偏好描述表引用一次**（表项在文件 `0x950478`，16 字节步长，形如 `{name_ptr, type=2, default=0, ...}`），**没有任何 `push imm32` 代码引用**。→ 运行时值落在 `.data` 的某个字节，读取点走结构体偏移，静态定位不可行，必须动态。
- **颜色不是常量**：整文件扫描 DWORD `0xFF73FF00` / `0x73FF00` / `0xFF8C4000` 全 0 命中 → (115,255,0) 等像素色由浮点基色/材质调制算出，不能靠常量下断点。
- **Game.dll 是 ASLR 的**：本次进程里 `.data` 载入在 `0x584E9000`（即镜像基址 `0x4F990000`），不是 PE 首选基址 `0x6F000000`。→ 所有运行期地址必须用 `warcraft3::get_war3_searcher().base()` 换算；跨进程比较只能按「节名 + 节内偏移」。
- **偏好只被读一次**：改注册表要重启才生效（实测），跑图过程中改 `.data` 里的值若被测点每帧读取则会立刻生效——这一点正是 S0 的验证手段。

## 4. 阶段划分

### S0 定位偏好字节（进行中）

- 工具：`src/src/extensions/memprobe.cpp`（新增，env 驱动，无行为影响）
  - `JAPI_MEMPROBE=<dir>`：注入时起线程，每 4 秒把 Game.dll **可写段** dump 成 `<tag>-tNN.bin` + `<tag>-tNN.txt`（节名/运行期 VA/大小/在 blob 内偏移）。
  - `JAPI_MEMPROBE_TAG=<tag>`：文件名前缀。
  - `JAPI_MEMPOKE="0xADDR=0xVAL;..."`：t≈14 个 tick 时进程内改写字节并 dump，用于验证。
- 采集：三次部署，注册表 `healthbars` 分别为 0 / 1 / 0（`build/gather_pref.ps1`），每次 9 个 dump。
- 判据（`build/prefguess.py`）：字节必须
  1. 在**同一局内绝对稳定**（偏好开机读一次，之后不再写），且
  2. `a=0, b=1, c=0`（或 1/0/1）。
  时序噪声（计数器/计时器/RNG）局内不稳定，会被过滤掉。
- 验证：pref=0 的一局里用 `JAPI_MEMPOKE` 把它写 1 → 屏幕立刻出现引擎原生条即确认。
- 预期：候选字节个位数；半天内完成。

### S1 常显（S0 成功即可交付）

- 注入后把偏好字节置 1 → 整局原生条常显，锚点/遮挡/宽度全原生，D3D 自绘条可关。
- 对外 API：`jass.runtime.native_bars(true|false)`（默认按地图配置），D3D 条保留为回退开关。
- 验收：`-Demo` 全绿；截图与「注册表 healthbars=1」的原生条像素级一致（位置/色/宽高）。

### S2 定制（探索，以 S0 得到的地址为锚点）

- 从偏好字节反查读取点：capstone 线性反汇编 `.text`（已装 capstone 5.0.7），找 `[abs]` 与 `[reg+disp]` 引用，得到「画不画条」的门控点。
- 沿门控向上找到「按单位决定画/不画、多大、什么颜色」的逻辑，用点 patch（nop / 强制 true）逐步确认。
- 产出目标（对齐社区 memoryhack 的三个 API）：只给指定单位显示、HP 分档换色、hover 高亮、按单位类型缩放。
- 风险：引擎可能批量提交所有条（一次 draw 画全部），那时要改的是「生成条几何」的函数而不是 draw；1.27a 代码结构未知，预留 1–2 天。

### S3 收尾

- D3D 自绘条降级为 fallback（默认关，保留开关）；回归 `116/116` + D3D `147/147` 不退化；`docs/STATUS.md` 更新；提交。

## 6. 与「保持 D3D 自绘」的对比

| 维度 | D3D 自绘（现状，33/33 通过） | 引擎原生（本路线） |
|---|---|---|
| 跟随延迟 | 半帧~数帧（采样率上限） | 0（同帧） |
| 锚点 | 按类型实测常量（`BAR_HEAD`），地形高度参与 | 模型 overhead 附着点，天然正确 |
| 遮挡 | 需要我们自己排 draw 顺序 | 引擎自带 |
| 尺寸 | 我们按原生实测复制（85×9 等） | 原生（含按类型宽度） |
| 定制能力 | 完全自由（颜色/形状/进度条样式） | 需 S2 逆向后才能改 |
| 风险 | 低（纯 overlay） | 中高（版本绑定 patch） |

## 7. 本轮实测数据（S0 采集）

- Game.dll 可写段只有 `.data`：`size=0xA163C`（660,540 字节）。
- 每局 9 个 dump（t=4..36s），三次部署分别落在 `build/pref-a`、`build/pref-b`、`build/pref-c`。
- 同局 t02 vs t06 的朴素差分：3621 个字节变化、65 个「0/1 布尔」噪声候选 → 说明必须用「局内稳定 + 三局交叉」过滤（`build/prefguess.py`）。
